# Decisions

## 2026-11-04 — first build scope

The first build is a thin vertical slice of Phase 1: create a lab, connect Dropbox read-only, list and hash files, extract text, and run keyword + vector search with previews.

Labels, corrections, Needs a look, protocol pages and Frigade onboarding come in later builds.

Why: it's the shortest path to the pilot's first goal (find X in under 10 seconds) and tests the content-hash data model before labels depend on it.

## 2026-11-04 — file sources

One `Source` interface with two adapters: a local-folder adapter for tests and dev, and a Dropbox adapter (read-only scopes, `list_folder` cursors) for the real manual check.

Why: tests stay fast and offline, and Phase 2–3 sources (upload, instrument) slot into the same interface.

## 2026-11-04 — database and auth

Hosted Supabase (free project) for dev and the pilot: Postgres + pgvector, Supabase Auth with email magic links, RLS policies on `auth.uid()` via `members`.

Tests run against local Homebrew Postgres 17 + pgvector (`brew install postgresql@17 pgvector`) with a small stub of Supabase's `auth.uid()` (reads `request.jwt.claims`), so lab-isolation tests run offline.

Why: no Docker on the dev machine; dev matches the pilot; tests stay fast.

## 2026-11-04 — embeddings

Local `Qwen/Qwen3-Embedding-0.6B` in the Python worker (sentence-transformers, MPS/CUDA when present), 1024 dims → `chunks.embedding vector(1024)`. Queries get the model's instruction prefix; documents don't. Store the model name with each chunk so a swap can re-embed.

Why: $0 per file, lab text never leaves our machines, and stronger retrieval than bge-small on tables, units and sample IDs. Behind the one model interface, so a hosted model is a one-file swap.

## 2026-11-04 — query embedding at search time

The Python worker also serves a small FastAPI `POST /embed` for search queries; the Next.js search route calls it with a ~250 ms timeout. On timeout or error, search returns keyword-only results and the UI says so.

Keep Qwen3-Embedding-0.6B (embeddings decision above). Measure p50 query-embed latency on the target worker host; if it exceeds 150 ms, swap to `bge-small-en-v1.5` (384 dims) behind the same interface, with a migration and re-embed.

Why: one model on both sides keeps vectors comparable; keyword fallback follows "never block on AI".

## 2026-11-04 — extraction and previews in the first slice

Extract text-bearing files only: PDF (pdfplumber), Excel/CSV (sheet names, header rows, first rows, units), DOCX, TXT/MD. Images and unknown formats are indexed by name, path, dates and EXIF, with a thumbnail. Previews and thumbnails go to R2 under `<lab_id>/<sha256>`.

No OCR or image captions yet; those come with the labeling build (Tier 2 reads images).

Why: enough to test "find X in under 10 seconds" on real files without the cost and scope of image reading; R2 previews don't depend on Dropbox temporary links.

## 2026-11-04 — Supabase project and email

Dev uses the existing Supabase project `binarylabs` (us-east-1, ref `hstjkkdgvotrrqnmqppu`). The worker connects through the session pooler (port 5432), not the transaction pooler, because Procrastinate needs session features. Site URL is `http://localhost:3000`.

The free tier blocks email template edits on the default email sender, and that sender only allows a few emails an hour. Until a custom SMTP provider (likely Resend) is set up, invited people follow the default invite link and then sign in with a magic link; their `members` row already exists. Before the pilot: add SMTP and point the invite template at `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=invite`.

## 2026-11-04 — measured: query embedding and scan

Qwen3-Embedding-0.6B query embed over HTTP, p50 ~45 ms (three runs of 50: 41, 49, 48 ms) on an M4 Mac with MPS; ~563 ms on CPU for the same short query. Cost grows with query length (41 ms at 6 tokens, 97 ms at 84).

Scan of the 51-file sample lab: 24 s, ~97% of it embedding (~1k tokens/s on MPS). Lab text runs ~3 Qwen tokens per word because digits tokenize singly; chunks are sized by a token estimate, not word count.

Consequence: a CPU-only Fly/Railway worker would push every search past the 250 ms timeout into keyword-only mode. For the pilot, serve `/embed` from a machine with a GPU (the PRD's local GPU box or Modal), or swap to `bge-small-en-v1.5` per the earlier decision. Not settled yet.

## 2026-11-04 — labels: data model

Labels are keyed by `(lab_id, sha256)` like chunks, so a duplicate carries one label. `corrections` points at that pair, not at a `label_id`. Members never write `labels`: inserting a `corrections` row (through `correct_label` or `undo_correction`, both `security invoker`) runs a trigger that applies it as `auth.uid()` in the same statement and records the full state before and after. Sending the current values back records an acceptance. An undo restores the exact prior state, only for the person who made the change and only if nothing changed since. `experiments.protocol_id` waits for the protocols table. Members add and edit experiments and people; admins remove them.

## 2026-11-04 — labels: tiers and learning

Tier 2 is `claude-haiku-5-5` at low effort; Tier 3 is `claude-sonnet-5-5` at medium effort with the server-side refusal fallback on. Both return strict JSON (structured outputs), parsed again at our boundary; a malformed answer counts as no answer. Images get a Tier 2 description from their 640 px thumbnail, stored as an `image_caption` extraction and chunked for search. Model answers are cached in `model_calls` by (lab, sha256, purpose, model, prompt version), which is also the cost ledger. Without `ANTHROPIC_API_KEY` labels come from Tier 1 rules alone, capped at 0.8 confidence so a rules-only label always gets a glance.

A correction teaches folder rules (this folder means this experiment or person) and name templates (files named like `plate07_read1.csv` are named "Plate 07 … read 1"), stored in `label_rules`. Learning waits 15 s so an undone correction is never learned; undoing a learned one deletes its rules. Similar files are re-suggested from cached answers without new model calls: a taught rule lifts `check` to `suggested`, never to `accepted`, and leaves `needs_look` alone.

## 2026-11-04 — amber marks "check this" too

The PRD reserves amber for flags and "check this" labels; the earlier visual-system entry said flags only. Amber now marks `check` labels as well, and nothing else in the app uses it. Base's warning text on warning background measures 2.83:1 light and 1.95:1 dark, so the pair is Base's yellow tag colors: `#845201` on `#FDF2DC` (5.93:1) light, `#F3DCAE` on `#39240A` (10.95:1) dark.

## 2026-11-04 — measured: label eval on the sample lab

`sh workers/scripts/eval_labels.sh` (real models, clean database, 51 files, 46 unique): 89.1% accepted without edits (41/46). Name 89.1%, date 89.1%, experiment 97.8%, person 95.7%, instrument 93.5%. Every miss was a file sent to Needs a look (three unreadable formats, one unlabeled phone photo, one file whose folder and content disagree); no suggested label was wrong. Cost $0.0029 per file, 93% of it Tier 3: Haiku rates itself under 0.85 on most files, so 34 of 46 went on to Sonnet. 29 of 46 labels carry the "check this" marker. A run on the same code a few minutes earlier scored 87.0%, so expect a few points of run-to-run spread. The thresholds remain the PRD's starting guesses.

## 2026-11-04 — protocols and tutorials

Protocols and tutorials live in our database, not in Dropbox, because Dropbox access is read-only. One `protocols` table with `kind` (`protocol` or `tutorial`); a tutorial is a how-to page that never carries expected values. Every save inserts an immutable `protocol_versions` row (title, Markdown body, `expected_values` JSON left empty until Phase 4, author, note) and moves `protocols.current_version_id`, so a Phase 4 flag can cite the exact version it checked against. A save names the version it started from and fails if someone saved in between, so two people never overwrite each other silently.

The body is Markdown, rendered without raw HTML. Steps are a numbered list in that Markdown; a structured step model waits for Phase 2's voice-to-steps. A page links files from the index (a demo video, an example gel, the original .docx), each opening in Dropbox like any search result. "Start from a file" fills a new page with an indexed file's extracted text and links that file, so a lab's existing protocol documents become pages without retyping; no model rewrites them. `experiments.protocol_id` now points at `protocols`.

Members create and edit; admins archive. Archiving hides a page but keeps its versions, since flags may cite them. Search shows matching protocols (keyword match on title and body) above files. Every create, edit and archive goes to `audit_log`.

## 2026-11-04 — deleting a lab and disconnecting Dropbox

**Delete the lab** is an admin action in Settings, confirmed by typing the lab's name. It takes effect at once: the lab disappears for every member (membership checks treat a lab marked for deletion as gone), the Dropbox token is deleted and revoked with Dropbox, and scans stop. A worker job then removes the lab's previews from the preview store (everything under `<lab_id>/`), deletes the lab row so every lab-scoped row cascades away, and deletes blobs and extractions that no other lab still references. It runs within minutes, well inside the PRD's 7 days, and is safe to re-run if interrupted. A `lab_deletions` row keeps only the lab id, who asked, when, when it finished and row counts, so we can prove the deletion happened without keeping any lab content. There is no undo; the lab's own files in Dropbox are untouched and could be indexed again, but protocols exist only with us, so the confirmation offers a Markdown download of every protocol first. The PRD's confirmation email waits for the mail service (Resend); until then the person who deleted sees a confirmation page.

**Disconnect Dropbox** is an admin action on the Dropbox section. It deletes the stored token, revokes it with Dropbox, and stops scans at once. The index stays searchable, previews keep working, and "Open in Dropbox" links still work for anyone with Dropbox access. Connecting again resumes from a fresh listing.

## 2026-11-04 — Phase 2 starts; uploads and our own storage

Phase 2 starts at the operator's call, before the Phase 1 pilot gates in the PRD have been measured in a real lab. Build order: uploads and storage first (they decide Phase 2's "done when"), then voice talk-through to steps, then procedure videos.

Uploaded files are stored whole, content-addressed, in the same object store as previews (R2 in the pilot, a local folder in dev and tests), under `<lab_id>/files/<sha256>`, so lab deletion's prefix delete covers them. The PRD's ~2 MiB content-defined shards and manifests wait for Phase 3: they pay off for large instrument files and resumable uploads, not for bench photos and screenshots. Each lab gets one `upload` source; an uploaded file is a `file_locations` row on it and goes through the same scan, extract, label and search pipeline as a Dropbox file. Uploads are the first data we hold that the lab has no other copy of, so they count toward deletion and need a download path.

## 2026-11-04 — speech-to-text: ElevenLabs, with local Whisper as the alternative

Talk-throughs are transcribed by ElevenLabs speech-to-text (Scribe) by default; the operator has ElevenLabs credits. Local Whisper (faster-whisper) on our own machine is the second implementation behind the same interface, chosen by config, for a lab that wants audio never to leave our machine or once a GPU worker exists. The transcript is stored as an extraction, so it's cached and searchable like any other text; a model then turns it into numbered steps that a person reviews before they become a protocol version. Needs `ELEVENLABS_API_KEY` in `.env`.

## 2026-11-04 — uploads: the first slice

Phones and desktops upload into our store; videos wait for a later slice. Choices made while building it, beyond the entry above:

- **50 MB per file.** Phone photos run 2–12 MB and lab PDFs and screenshots less; the cap keeps one request finishable on bench Wi-Fi (about 80 s at 5 Mbps) and bounds the worker, which reads a whole file into memory. Video and audio are refused outright.
- **The web app records the location, the worker writes the blob.** `record_upload` inserts the `file_locations` row; the worker computes the file kind and MIME type from the bytes as it does for Dropbox files, so that logic stays in one place.
- **One location per content per lab.** `external_id` is the sha256, so a retried or repeated upload returns the first location and keeps the first sender and experiment.
- **No new job.** The web app still never enqueues: `record_upload` sets `scan_requested_at` on the upload source, and a scan of an upload source lists nothing and hands its pending locations to `process_location`. Uploads are labeled within about 30 s of arriving on a laptop worker.
- **The sender and their day are label facts.** The sender becomes a `people` row linked to their membership, named from their profile or email. The day is the sender's local date, so an evening upload isn't dated tomorrow.
- **Uploads browse under "Uploads", one folder per experiment.**
- **Uploaded files open from our store** through `/api/files/<location>`, inline only for types that can't run script, and each open is audited.
- **Installable without a service worker.** Chromium reports the app installable with the manifest alone, and nothing of a lab's is cached offline.
- **Env names stay** `PREVIEW_STORE` and `PREVIEW_DIR`, now meaning the object store; renaming them would touch every deployment for no behavior change.

Open: the route takes the file through our server. On a host with a small request limit (Vercel functions take 4.5 MB) uploads would need a presigned PUT straight to R2 instead. HEIC files upload but the worker can't render them yet, so they fail at the preview step; iOS usually hands the browser a JPEG.

## 2026-11-04 — talk-throughs: the first slice

A protocol or tutorial page, the protocol list and "New page" offer "Record a talk-through". The recording goes up through the upload route, the worker transcribes it and drafts steps, and the person reviews the draft beside the transcript before "Use these steps" opens the editor. Choices made while building it, beyond the speech-to-text entry above:

- **30 minutes per recording, 100 MB per audio file.** One procedure told aloud usually takes 2 to 15 minutes. At 64 kbps, 30 minutes is about 15 MB, which goes up in under 30 s on 5 Mbps bench Wi-Fi, and its transcript (about 4,500 words) is an easy draft for the model. The recorder stops by itself at the cap and warns two minutes before. 100 MB leaves room for a longer or less compressed voice memo picked from the phone. The 50 MB cap for photos and documents is unchanged.
- **Opus in WebM where the browser has it, AAC in MP4 on Safari.** WebM sniffs as video, so the recorder names its files `.weba` and the worker knows them by extension.
- **The upload route takes the recording.** An `x-upload-purpose: talk-through` header picks the audio cap and `record_talk_through`, which records the file like any upload (under `/Uploads/Talk-throughs/`) and starts the talk-through in the same transaction. Plain uploads still refuse audio.
- **Only talk-throughs are transcribed.** The worker transcribes a location that has a `talk_throughs` row, whatever its bytes sniff as. Audio in a lab's Dropbox, or sent as a plain upload, is indexed by name, so nobody pays to transcribe an archive by accident.
- **The transcript is an extraction**, keyed by the transcriber's name and version (`elevenlabs/scribe_v2`, `whisper/small`), chunked and embedded like any text. The same audio is never transcribed twice by the same transcriber, in any lab. Each transcription is a `model_calls` row (purpose `transcript`) with its seconds and cost: Scribe v2 is $0.22 an hour.
- **Steps come from Tier 2** (`claude-haiku-5-5`, medium effort), as the PRD places talk-throughs: rewording what someone said into steps is a narrow job, and a person checks every draft. The model returns strict JSON (title, materials, steps, cautions), told to use only what was said and to keep numbers as spoken; we write the Markdown, so the steps are always a numbered list and empty sections are left out. The answer is cached in `model_calls` (purpose `steps`).
- **A draft never applies itself.** It's stored on the talk-through. "Use these steps" saves through `use_talk_through`, which creates the page or saves on top of the version that was on screen while recording (so anyone's save since is caught, as in the editor), links the recording to the page and marks the talk-through used, all in one transaction. An existing page keeps its title.
- **Every state is visible.** Transcribing, drafting, ready, failed with Retry, or no draft (no model set up, no speech heard, or nothing like steps), which offers the transcript to start from instead. Without `ANTHROPIC_API_KEY` talk-throughs still transcribe and the transcript is the starting point.
- **Each paid job runs once at a time.** Transcription and drafting jobs carry procrastinate's execution lock as well as the queueing lock, so a rescan or the 10 s sweep can't start a second paid call beside a running one.

Measured: a 35 s spoken clip (`scripts/e2e-talk-through.sh`, real ElevenLabs and Claude on local Postgres) was transcribed and drafted 10 s after the worker started, for $0.0022 transcription and $0.0005 drafting. The audio's label adds $0.0003, or $0.006 when Haiku is unsure and Sonnet runs.

Open: the worker holds a database connection while it transcribes, which for 30 minutes of audio can take a few minutes. Local playback in dev serves the whole file without range requests, which Safari may refuse to play; R2 in the pilot answers ranges. A recording re-sent for another page returns the first talk-through.

## 2026-11-04 — procedure videos

A protocol or tutorial page has a Videos section above its files. "Add a video" records with the phone's camera, picks a video file, or links a video already in the lab's index; each plays in the page, with a poster, and search finds what's said in it. This finishes Phase 2's build order. Choices made while building it:

- **A video is a protocol file whose blob is a video.** Blobs get a `video` kind (0011 refiles videos indexed before it). An uploaded video waits in `pending_protocol_files` until the worker has read the stored bytes and hashed them; only then is it linked, as the person who added it, so the page's membership and archive checks run and the audit log names them. Nothing is linked by a sha256 nobody verified: extractions and transcripts are shared by hash, so a claimed hash could read another lab's text.
- **500 MB per video, sent straight to the store in 8 MiB parts.** Phones record 1080p at 100 to 200 MB a minute, so 500 MB is 3 to 5 minutes, enough for one technique. On 5 Mbps bench Wi-Fi it takes about 13 minutes to send; a dropped connection costs one part (about 13 s), retried after 2, 5 and 15 s and then on Retry or when the browser is back online. Storage doesn't set the cap: a video at the cap is $0.0075 a month at R2's $0.015/GB, and a lab with 100 of them holds 50 GB, about $0.75 a month, inside the PRD's line for owned files. Transfer time and the worker's memory set it. A longer video gets "trim it in Photos first".
- **The server stays the authority.** Starting checks the page and the cap and opens a multipart upload at `<lab_id>/uploads/<upload id>`, a staging key under the lab's prefix. Each part goes to a presigned R2 `UploadPart` URL with its size signed in, or, with the local store, to our own route. Completing joins the parts, checks the size, reads the object back and computes the sha256 on the server, copies it to `<lab_id>/files/<sha256>`, and only then calls `record_video`; the staged copy is dropped after that, so a complete that fails part way can run again. A part URL can't name a size over the cap, so one session stages at most 500 MB. Every key is built from the session's lab. Reading 500 MB back from R2 costs no egress and a few seconds on a hosted server. Parts live in the page's memory, so an upload survives dropped connections but not a reload, as the upload queue does.
- **Playback is an HTML video element on `/api/files/<location>`.** The local store answers byte ranges itself (206, `Content-Range`); R2 answers them behind a presigned redirect, which for a video lasts four hours because browsers send later ranges to the URL they were redirected to (other files keep the one-minute link). `video/mp4`, `video/quicktime` and `video/webm` are served inline with `nosniff`; anything else still downloads. A video asks for many ranges as it plays, so only the request that starts at byte 0 is audited as a download. No transcoding: a phone's HEVC MOV plays where the browser decodes HEVC (Safari, most Chrome on Mac and recent Windows).
- **A Dropbox video plays through a temporary link.** The server mints the lab's access token, calls `get_temporary_link` (covered by the `files.content.read` scope we already hold) and redirects to Dropbox's four-hour link; "Open in Dropbox" stays. It's feasible because it needs no new scope and the token never leaves the server, and fair because members already see every indexed file's preview and text. Only video types take this path; other Dropbox files still open in Dropbox.
- **Posters come from ffmpeg, an optional system dependency.** The worker takes the frame at 1 s (or the first frame of a shorter clip) as a 640 px WebP preview, stored like any other preview. Without ffmpeg, or for a frame it can't read, there's no poster and the file still indexes. There's no pure-Python fallback: nothing in pure Python decodes H.264 or HEVC, and PyAV would bring its own copy of ffmpeg's libraries. `FFMPEG_PATH` points at it when it isn't on `PATH`.
- **Only a video on a page is transcribed**, as only a talk-through is. Every 10 s the worker gives each video blob on a page a `videos` row and transcribes the waiting ones: ffmpeg takes the first audio track as mono 16 kHz AAC (about 22 MB an hour), the configured Transcriber hears it, and the transcript is an extraction keyed by the transcriber, chunked and embedded in that lab. The job is locked per video, and the extraction is cached, so two labs or pages linking the same video pay once; the lab whose copy was heard gets the `model_calls` row. States are waiting, ready, failed (Try again) and unavailable: no sound, a Dropbox video over 500 MB (it plays but isn't read whole into the worker), or no ffmpeg.
- **Deletion and isolation.** `videos` and `pending_protocol_files` are lab tables with RLS (members read them; members can take a pending video off a page), and `videos` is a blob reference. Staged parts, stored videos and posters all sit under `<lab_id>/`; deleting a lab in R2 also aborts open multipart uploads under the prefix, since parts aren't objects a listing finds.
- **"Draft steps from this video" came later** (see "steps from a video"). Recording in-app with `MediaRecorder` was left out: the phone's own camera records better video.

Measured: a 14 s spoken clip (`scripts/e2e-video.sh`, 2.8 MB, real ElevenLabs on local Postgres and the local store) went up in one part, was linked with a poster, and was transcribed and searchable 6 s after the worker started, for $0.000853.

Open: the R2 path (multipart, presigned parts, read-back) and Dropbox temporary links are built against their APIs but untested against a live bucket and account; R2 needs a CORS rule that allows PUT from the app's origin and exposes `ETag`, and a lifecycle rule that aborts incomplete multipart uploads after a day, since the server keeps no list of open sessions and an abandoned one otherwise waits for lab deletion. The worker reads a whole video into memory, up to 500 MB, so a hosted worker needs room for it. Bytes moved to `<lab_id>/files/<sha256>` stay if `record_video` then refuses (an archived page), until the lab is deleted, as with uploads.

## 2026-11-04 — naming and copy rules

From the first signed-in walkthrough. One word for one thing, in the words a grad student uses:

- **Protocol** is the thing under Protocols ("New protocol", "Archive"), with Protocol or Tutorial as its kind; "page" is gone from buttons and empty states.
- **File** for anything in the lab, **upload** for what came through the app; never source, location, blob, extraction or tier.
- **Talk-through**, **Check this** and **Needs a look** stay: they name things a person acts on.
- Help text is one short sentence, or none when the screen says it already. An empty state says the next step in one line.

## 2026-11-05 — Phase 3 starts with the parts that don't need the pilot lab

Phase 3 (Connect) starts at the operator's call while Phases 1 and 2 wait for a real lab. The instrument parsers wait for the pilot lab's top five instruments; two pieces don't depend on them and start now.

**Instrument uploader.** A single Rust binary, Windows first, that watches one or more folders on an instrument PC and sends each new or changed file to the lab. ## 2026-11-05 — data sheet to chart: the first slice

A spreadsheet or CSV's opened row (in search, Browse and a protocol's Files) offers "Make a chart" beside its other actions and lists the charts already made from it. The builder at `/charts/new?file=<location>` shows the file's table on the left (a sheet picker, then each column with its letter, unit and whether it holds numbers or text) and the live chart on the right, with its type, series, axes, legend and an optional protocol under it. A saved chart lives at `/charts/<id>`, and a protocol it names draws it in a Charts section under Videos. Choices made while building it:

- **Tables are parsed while a file is processed.** The bytes are in hand then, so a chart never waits for a second download, and the builder opens at once. A spreadsheet indexed before charts existed, or one whose table failed, is asked for when someone opens the builder (`request_data_table` sets it waiting) and the worker's 10 s `tend_tables` reads it again; the web app still never enqueues. On a laptop the three fixture exports were ready 3 s after the worker started, and a file asked for again 8 s after the ask.
- **One columnar JSON per file per lab**, at `<lab_id>/tables/<sha256>.json`, so deleting the lab's prefix removes it. `data_tables` records it by (lab, sha256) with the parser's version, and a ready table at the current version is never parsed again.
- **200,000 cells per file.** Measured on a 40,000-row, 9-column export of 3-decimal values: the worker kept the first 22,222 rows in 0.27 s, as 1.5 MB of JSON that gzips to 0.64 MB, about a second on 5 Mbps bench Wi-Fi. A 2 h kinetic read of a 96-well plate is 24k cells, a full spectrum scan of one 38k, an AKTA run with eight curves 48k. The budget is shared so small sheets stay whole and big ones split the rest; a cut table says "First 20,000 rows of 85,312." under the chart. Also 32 sheets, 512 columns and 200 characters a text cell.
- **What the parser reads.** The header is the first mostly-text row as wide as the table with data under it, so instrument preambles become notes shown above the columns. A second header row of units (AKTA's `ml`, `mAU`) or sub-names (`Rep 1`) joins the first, with a name written once covering the columns to its right. Units come from a trailing parenthesis or bracket. A column holding mostly numbers is a number column, and its odd cells (`OVRFLW`, `n/a`) are blanks counted as "not numbers". `h:mm:ss` reads as minutes, hours or seconds by its length. Decimal commas are read when the separator isn't a comma, UTF-16 files (UNICORN's exports) are decoded, merged cells are read from the sheet's XML and fill every cell they span, blank rows split one sheet into several tables, and a plate grid with a blank corner keeps its row letters.
- **Specs name columns by letter**, which stays put however a column is named. `chart_spec_ok` in SQL mirrors `ChartSpec` (zod); the save route also checks every column against the stored table, and refuses text on a number axis or more than 60 bars. Members create, edit and delete charts; each is a `chart.create`, `chart.save` or `chart.delete` in the audit log. A save names the `updated_at` it started from, so two people never overwrite each other silently.
- **Hand-rolled SVG, no chart library.** Linear and log ticks, lines, dots, bars, error bars, a legend, a hover readout and a table of the numbers come to about 950 lines (`chart-geometry.ts`, `chart-svg.tsx`, `chart-figure.tsx`); the builder's chunk, export included, is 39 KB minified and 13 KB gzipped. Recharts, visx and Plotly would each have cost more than that for features we don't use, and an exported SVG from our own markup is clean.
- **Six series colors.** The dataviz reference hues in the order blue, orange, aqua, violet, magenta, green, which passes its colorblind checks on our surfaces (worst neighbors 9.2 light and 9.4 dark, normal vision 19.7). Yellow is left out because amber means Check this, and red because it reads as an error and dropped the order's worst pair under the target. A scatter takes three series, the most its checks allow when any two dots can touch; lines and bars take six. Aqua and magenta sit under 3:1 on the light surface, so every chart has "Show the numbers" and a legend once it has two series.
- **Export is client side.** SVG and a PNG at twice 960 by 560, with the title on the figure, in the light colors on white, as a printed figure would be.

Not built at first, and built since (see "dates along x" and the four entries after it): per-series x columns, dates along x, a sweep that re-parses tables after a parser version bump, heatmaps of plate grids, and more than six series.

## 2026-11-05 — the instrument uploader

Built as the Phase 3 entry above describes. An admin adds an instrument in Settings > Instruments, reads off a pairing code, and runs `binary-labs-uploader pair <server> <code>` on the instrument PC; from then on new files in its watched folders show up under Browse at Instruments/<name>/. Choices made while building it:

- **One table, one source per instrument.** `instruments` holds the name, who added it, the pairing code's hash and expiry, the device token's hash, and when it paired, was last seen and was revoked. Each instrument gets its own `instrument` source, so a token's reach is one `source_id` and Browse, deletion and counts need nothing new. Members read instruments through `lab_instruments` and column grants that leave out both hashes, because an 8-character code is guessed from its sha256 in seconds.
- **Codes are 8 characters of Crockford base32**, shown as `K7QM-4XPA`, good once for 15 minutes; typed codes ignore case, spaces and dashes and read O as 0 and I or L as 1. An instrument pairs once. A code that ran out gets a new one; a PC that's reinstalled is revoked and added again, and its files land in the same Browse folder if it keeps its name. Ten wrong codes from one address in 15 minutes, or a thousand from everyone, stop pairing for a while.
- **Device tokens are `blu_` and 32 random bytes**, stored as their sha256 and handed only to the uploader. The uploader's routes live under `/api/instruments/`, which the session proxy skips, and read only `Authorization: Bearer`; session routes read only cookies, and a Supabase JWT never has the prefix. The database functions behind them (`pair_instrument`, `instrument_session`, `record_instrument_file`) take the token's hash and are granted only to the service role, so the database, not the route, decides which source a token writes to; pairing has no session, and its rate limit has to trust the address our server passes in.
- **Files go through the videos' multipart path, now shared** (`lib/staged-upload.ts`): start, a presigned part URL or our own part route, then complete joins the parts, reads them back, checks the size and the claimed sha256 on the server and only then copies them to `<lab_id>/files/<sha256>`. "Do you have this file?" answers yes when the lab's store already holds those verified bytes, from any path or an upload, and records the new path without a byte sent; it never looks across labs. A file's location keeps its path on the PC as `external_id` and its sha256 as `source_rev`, so an export the instrument rewrites in place is one file that is indexed again.
- **500 MB per file**, the same as videos. Instrument exports are KB to a few hundred MB; the worker still reads a whole file into memory, and an imaging stack bigger than that waits for content-defined shards. The uploader skips a bigger file and lists it in `status`.
- **The instrument is a Tier 1 fact at the strength of a person's correction**, not merely strong: the lab named the instrument that sent the file, which is surer than a SpectraMax signature in its header, so a header never conflicts with it. It stays on a Needs a look label too, since it isn't a guess.
- **The uploader is one Rust binary** (`instruments/uploader`, `ureq` with rustls, `notify`, `sha2`, no async runtime). A file is sent once its size and modified time have held for 10 s and, on Windows, it opens without a sharing violation; it is hashed streaming and re-checked after. Its queue and confirmed parts live in a JSON file written atomically after every part, so a reboot sends only the missing parts. It runs from Task Scheduler at the paired user's log on rather than as a Windows service: no service code or crate, `run` already rides out every transient error, and the task runs as the user whose settings hold the token. Settings live in `%LOCALAPPDATA%\Binary\uploader`, so roaming profiles don't copy the token.
- **Settings > Instruments** lists each instrument with when it last checked in and how many files it sent; an admin adds one, sees the code once with the four commands to run, and the panel turns to "Paired" by itself. The drawing is a gray benchtop reader with its plate drawer out, gray because the tiles beside it are already blue and green.

Measured: `scripts/e2e-instrument.sh` paired the real release binary with the real route handlers on local Postgres and a local store (only the database client swapped for plain Postgres), refused a wrong and a used code, and sent a CSV, a file written over 10 s and a 20 MB file. Killed after the 20 MB file's first part, the restarted uploader sent parts 2 and 3 only. The growing file was recorded 22 s after writing began, at its final size; a lock file and a `.tmp` file were never sent. The worker indexed and labeled all three with the instrument within 2 s.

Open: Windows-only behavior (the sharing-violation probe, hidden and system attributes, `notify` on NTFS, Task Scheduler's defaults) is built and type-checked but runs for the first time on the CI Windows runner and then a real instrument PC. The exe needs Windows 10 or later. There's no download page for it yet; the admin gets it from the CI artifact. R2's presigned part path is the videos' path, still untried against a live bucket.

## 2026-11-05 — the lab calendar

- **The record is never stored.** `calendar_files` dates each file (one per sha256, as search shows it) by its label date, or else the day its newest live copy was modified where the viewer is, which is how search rows already date a file. Its kind follows that copy's source: a Dropbox file, an upload, or an instrument's file; talk-through recordings are left out since the talk-through is on the record itself. `calendar_events` adds protocol versions (of live protocols), charts and talk-throughs on the day they were made. `calendar_record` counts both per day, kind and group (an experiment for files and uploads, the instrument for its files, the protocol for its saves), so a day reads "342 files · P450 BM3" however many files there are. A 42-day month grid of a 20,000-file lab counted in 248 ms on a laptop's local Postgres (`test_calendar_db.py`). Opening a day lists its plans, then each group with its first eight files as search rows (preview, labels that edit in place, Open) and "Show 50 more"; protocol saves, charts and talk-throughs link to their pages.
- **Filters** are experiment, person and instrument, on both halves. A person matches a file's label, or what their membership made; an experiment matches a file's label, a chart's file, and the protocol the experiment uses; an instrument matches its own files and files whose label names it, and no protocol saves, charts or talk-throughs.
- **Plans are `calendar_entries` rows** (0017): a title, notes, either `starts_on`/`ends_on` dates (all day, the end included, never shifted by a zone) or `starts_at`/`ends_at` instants (the end excluded, shown on the viewer's clock), and links to an experiment, a protocol, an instrument (`instruments`) and people. People are an array of `people` ids on the row, so a save is one statement; the trigger checks new ones are in the lab and drops removed ones. Members write the table directly under RLS with column grants, as with charts; triggers keep links in the lab (`BL401`, `BL103`), refuse an archived protocol (`BL102`) or a removed instrument (`BL402`) when the link changes but keep one already there, and write `calendar.create`, `calendar.save` and `calendar.delete`. A save names the `updated_at` it started from, so two people never overwrite each other silently. Who made an entry is kept and shown.
- **Saving is Notion's: every change saves as it's made.** A pick saves at once, the title and notes when you leave them; a new entry saves once it has a title. Writes go on screen at once and to the server one at a time per entry, each on the version the last returned, so a drag and an edit don't collide. Deleting asks once and offers Undo.
- **A double booking is a notice, not a stop.** When an entry names an instrument, the editor asks `calendar_overlaps` for other entries booking it at an overlapping time (an all-day entry holds its days midnight to midnight where the viewer is) and says so in one quiet line.
- **Dragging has keyboard twins.** Alt and an arrow moves an entry a day (Up and Down a week in the month, a quarter hour in the week's grid); with Shift it changes the end. Each move is announced. Days move on the wall clock, so 9 am stays 9 am across a DST change.
- **DST.** The week's grid is 24 wall-clock hours: on the day the clocks go back the repeated hour is drawn once and entries in it overlap, as on paper; on the day they go forward the missing hour is just a line. A time typed into the gap moves on by the gap (2:30 becomes 3:30), and an ambiguous one is the first. Tested on the week of Nov 1, 2026 in New York.
- **Color.** The six record kinds wear the charts' six series hues in their validated order, as a small dot beside words that already name the kind (blue files, orange uploads, aqua instrument files, violet protocol saves, magenta charts, green talk-throughs); aqua and magenta sit under 3:1 on white, which the words carry. Plans are neutral gray bars and blocks. No amber, and red only for Delete.
- **"On the calendar"** on a protocol's page lists its coming entries, each opening on the calendar.

Later the same day the operator asked for a day view and "some way to expand the calendar, maybe something next to the title… kind of like how Apple's calendar does it":

- **Four views: Day · Week · Month · Year**, with D, W, M and Y beside T for today. The arrows step a day, a week, a month or a year. The day view is the week's grid with one column (the all-day row and the day's record lines on top, drag to create, move and resize, Alt and the arrows, the current-time line), beside the day's record in full: the day panel's own pieces (`DayRecord`), so files are the same search rows. A record line over the hours scrolls the list to its group. The day panel gains a "Day view" button. On a phone the switch shows all four; Day is a list of the day's plans and record with the arrows stepping a day, Week and Month stay the agenda, Year is two columns of small months.
- **The year is Apple's: twelve small months.** A day with anything on the record is shaded in the neutral tertiary fill and a day with a plan has a small dot under its number, with a one-line key over the grid; no counts, no color ramp, since the year's job is finding a day, not comparing them. A month's name opens the month and a day opens the day view. The days are one tab stop; arrows move a day or a week and Page Up and Down a month. The marks come from `GET /api/calendar/year`, which reads `calendar_record` and `calendar_plans` two months at a time (each read stays within their 62 days) and counts per day on the server, so no migration. Six reads in parallel, against one for a month.
- **The title is the way to any month or year.** It's a button with a chevron, at half strength until hovered or focused and always full on touch screens: a cold read by a first-year stand-in never found it when the chevron only showed on hover. It opens a year stepper over a 3×4 grid of months, as in Apple Calendar. Picking a month keeps the view and carries the day of the month over where it can (Jan 31 in a week view lands on Feb 28); from the year view it opens the month. Typing digits fills the year field; arrows walk the months into the next or last year, Page Up and Down change the year, Home and End go to January and December. Years run from 1970 to 2100.
- **The address is the state.** `?view=&date=` (with `day=` or `entry=`) follows the screen; a new view or date is a history step, so Back and Forward retrace them, while opening or closing the side peek only rewrites the step. Without `view=` the calendar opens on the person's last view, kept per user in this browser's local storage, else Day on a phone and Month elsewhere. A link to an entry or a day never opens the year, which has no side peek.

Not built: recurring entries. A repeat rule is cheap to store but each of its edits ("this one or all of them"), drags, overlap checks and deletions needs occurrences with their own exceptions, which is more than this slice. Also not built: reminders, other labs' or Google calendars, and a calendar export (an `.ics` feed would need a token outside the session). Plans aren't in the protocol Markdown offered before deleting a lab, though like protocols they exist only with us.

## 2026-11-05 — the lab map

The operator asked for "a mind map like Obsidian that connects the notes, files, documents". Map, in the sidebar after Protocols, draws how a lab's files, protocols, experiments, people and instruments connect, and every file's opened row, protocol, experiment and person has a map of its own. Choices:

- **Only links that exist, drawn solid.** A label's experiment, person and instrument; a protocol's attached files, charts and talk-throughs; an experiment's protocol. A file is its content (sha256), as everywhere else, and a "Needs a look" label or an archived protocol draws nothing. An instrument is the label's text, lowercased, so "SpectraMax M5" and "spectramax m5 " are one dot. Free tags aren't nodes: they would add hundreds of dots that mostly say the same as the experiment.
- **Hubs first, files on request.** A flat 20,000-file graph is a hairball, so `/map` opens on the hubs (protocols, experiments, people, instruments) sized by how many files each holds, with the files two hubs share as faint lines, four per hub (all of them was 2,400 lines on the pilot-sized lab). Clicking a hub opens its 400 newest files, and a hollow dot stands for the rest, opening them as a search. Clicking a file opens its row in search; a protocol its page; an experiment, person or instrument a search of its files, as the rest of the app does. On a touch screen the first tap says what a dot is and the second opens it.
- **The map around one thing** is `/map?around=<node>`: depth 1, with a 1 step / 2 steps control. A hub shows 150 of its newest files one step out and 24 two steps out, and says how many it left out.
- **Similar in meaning**, off by default, adds dotted lines from each file to its nearest files. The worker keeps them (`bl_worker/neighbors.py`, migration 0021): a file's vector is the mean of its content chunks' embeddings (not chunk 0, the name and path, or two files in one folder would always be "similar"; a photo waits for its caption, since EXIF alone makes every photo from one phone alike), a trigger on chunks marks it stale, and every 10 s the worker redoes stale vectors and the lists they touch: its own, the lists holding it, and the lists of its 50 nearest it should now enter. When a quarter of a lab moved at once it redoes every list instead. Each file keeps its 5 nearest above a floor. The floor comes from the sample lab with Qwen (`scripts/measure_map.py calibrate`, 595 pairs of the 35 files with text): files of one procedure or one instrument's exports sit at 0.85 to 0.99, everything else at 0.73 or under (median 0.45), so it's 0.75. Lists are never computed per request.
- **Canvas, not SVG.** Measured headless (Chromium, 1440 by 900 at 2x) with nodes moving every frame as a layout does: SVG held 60 frames a second to 2,000 nodes, dropped frames at 5,000 (p95 33 ms) and ran at 12 a second at 20,000 (p50 83 ms); a 2D canvas held 60 at 20,000 (2.8 ms a frame to draw). WebGL wasn't needed. The layout is our own force simulation (`lib/map-layout.ts`: springs on links, Barnes-Hut repulsion, a pull to the middle), about 400 lines, so no graph library ships.
- **One SQL function per view, members only.** `lab_map`, `lab_map_hub` and `lab_map_local` check membership once and then read only that lab's rows as the owner; their helpers can't be called by members, and neither table of the neighbor cache can be written by one. Row-by-row RLS was most of the cost: on the pilot-sized lab the hub view took 3.1 s that way (with every shared line) and 0.29 s this way. Tests prove a member of another lab is refused and that a file both labs hold shows each lab only its own label and hubs.
- **Calm.** Thin lines one pixel wide at every zoom, small dots that never grow past 14 points on screen, names in the lab's text colors appearing as you zoom in and never written over one another, nothing glowing. Hubs take the charts' first three hues (protocols blue, experiments orange, people aqua), the three that pass the colorblind checks when any two dots can touch; instruments are rings in ink and files small gray dots, so a fourth hue never sits beside the others. Yellow and red stay out. The type filters are the legend.
- **Reachable without a pointer.** The canvas takes focus; arrow keys step to the nearest dot in that direction, Enter opens it, plus, minus and 0 zoom and fit, and what's focused is read out with its links. "Show as a list" gives the same nodes and links as text.

After that, one changed file redid 4 lists in 24 to 280 ms, ten redid 32 in 0.2 to 0.7 s, a hundred redid 522 in 2.2 to 3.2 s. 80,000 rows, exactly 5 a file on the generated lab. Not built: tags as nodes; similar-in-meaning edges in the hubs-only view (they're drawn between files that are showing); a saved camera or open hubs per person; a map in the opened row itself rather than a link to one. ## 2026-11-05 — checking results: expected values and flags

Phase 4 starts with its first part, at the operator's call: a protocol holds checks, every data file tied to it is checked by the worker as it arrives, and a result outside its range raises a flag people answer. Q&A and forked AI suggestions come later. Choices made while building it:

- **Four kinds of check, in a lab's words.** A standard curve's fit (R² of a straight line through the standards, least squares), a peak's position (where the highest reading sits along wavelength, volume or time), a value (the mean, highest or lowest of a column, or one cell picked by the text in its row or its number, such as a sample's 260/280), and controls (rows whose name has a word in it, such as "blank", must each read in range, or their mean must). The range is "at least", "at most", "between" or "around ± tolerance". A curve or peak with no columns named works them out: a concentration by name or unit (BSA, µg/mL) against the mean of the readings, or wavelength, volume or time against the first reading after it.
- **Columns are named as the file names them.** A check lives on the protocol and meets many files whose letters drift, so it names a column by its header ("A595"), by header and unit ("BSA (µg/mL)") or, failing both, by letter. With no table named, every table in the file is tried in order. The flag records what was actually read by letter.
- **Checks are protocol versions.** `protocol_versions.expected_values` holds them, shaped by `CheckSpec` (zod) and `check_spec_ok` (SQL), which agree key for key, nulls spelled out. Saving checks (`save_checks`) is a new version with the same text; saving the text keeps the checks (a trigger carries them forward, and members can't write the column directly). A check keeps its id across versions, so its answers add up. Tutorials carry none (`BL108`).
- **What a file is checked against.** The protocol of the experiment on its label (not a label waiting in Needs a look), and any protocol whose page links the file. The day's controls come from the file itself, or else from another file labeled with the same experiment and day; a control flag names the control file and rows, and what they vouch for is the file's other readings in the same column.
- **When.** Triggers put a file in `check_requests` when its table becomes ready, its label's experiment, day or Needs a look state changes, a tied protocol gets a new version or is archived, an experiment is tied to another protocol, or a page links or unlinks it; a ready table also asks again for the files of its experiment and day. `tend_checks` queues `run_checks` every 10 s, and processing and labeling queue it at once. A run reads the file's table JSON, evaluates every check and writes the results in one transaction, stamped with the request it answered, so a request made mid-run is run again.
- **Couldn't check is a result, never a flag.** A missing column, fewer than three points, standards that don't vary, a cut table (only the first rows were read) or no control rows: the run records `couldnt` and the reason in `check_results`, shown on the file's opened row.
- **Running again changes nothing.** A flag carries a digest of its rule, value and cells. A later run keeps an open flag whose digest matches (still citing the version that raised it), clears one that now passes, can't be checked or no longer applies (with that reason), and raises a fresh one when the rule or the data changed. Answers stay on the flag they were given to.
- **Zero flags without a source, in the database.** A `flags` row needs its protocol version (by foreign key, with the check in that version holding the same id, kind and range, checked by trigger), its file (a ready table of the lab, by foreign key), its table name, its columns by letter and its rows (a non-empty `int4multirange`), and a control check needs its control file, table, columns and rows; nothing else may carry them. Its value must be outside its range (`not range_holds`). Tests in `workers/tests/test_checks_db.py` and `apps/web/src/lib/__tests__/flags.db.test.ts` try each missing piece.
- **Answers.** Useful, wrong or known issue with an optional note, through `review_flag`; members may change only those two columns, and each answer is a `flag.review` audit row (each check save a `check.save`). An answer can change but not be taken back. "Wrong" offers "Edit this check's range", which opens the check editor on that check; saving there is a new version through the same path. Admins see each check's rate on the protocol page and in the editor: useful out of answered, with the counts.
- **Where flags show.** Amber, the colour kept for Check this and flags: a "Flagged" tag on the file's row in search, Browse and a protocol's Files (open flags not answered "wrong"), the flag at the top of the opened row's Checks, the protocol's Checks section, and the Flags queue in the sidebar with the count of unanswered flags beside it. A flag's page shows the value, the range and "from <protocol> v<n>", the file with Open and Make a chart, the standards or trace drawn, and the table with the rows read marked; for a control, the controls come first.
- **Not built:** controls found by column name (a plate's blank wells as columns in a kinetic read), fits other than a straight line (4PL, log-linear), per-check sample ranges such as "the samples must fall within the standards", flags on files that aren't data sheets, a sweep that rechecks after a parser version bump (the next ready table asks), and notifications. The Flags list shows open flags; cleared ones stay reachable from their own page.

Measured: `scripts/e2e-checks.sh` (real worker, local Postgres and store, rules-only labels) indexed, labeled and checked five files 4 s after the scan, raised exactly the two expected flags, and cleared the curve's 7 s after its range was loosened.

## 2026-11-05 — asking the lab, and suggestions that wait for approval

Phase 4's "Q&A over the lab's records" and "AI suggestions run in a forked copy and wait for approval". A question typed in the Search box ("what was the yield of P450 batch 3?") gets a short written answer above the search results, each sentence followed by the numbers of the sources it came from, and the sources listed under it. From an answer or a protocol page the AI can draft a new protocol version or label fixes; neither changes anything until a member approves it. Choices made while building it:

- **Asking is explicit.** Search still runs as you type and costs nothing. A query that reads as a question (ends in "?" or starts with what, which, when, how and the like) shows an "Ask the lab" row under the box, and Enter asks. Without `ANTHROPIC_API_KEY` that row says asking isn't set up, and search works as before.
- **The web server calls the model, not the worker.** An answer streams while the person waits, and retrieval must run as the asking member under RLS, which the web app's session already does. The worker's queue and its 10 s sweeps are for files. Calls go through one interface (`lib/json-model.ts`), with a fake in tests.
- **Retrieval reuses search.** `ask_context` takes `search_files`' top 6 files and each one's best 2 chunks (words first, then meaning), `ask_protocols` the matching protocols' current text, and a spreadsheet adds its parsed table: up to 3 tables, 40 rows and 600 cells a file, rows numbered and columns by letter so a cell can be cited as `Kinetics!C4`. The model sees those snippets under ids (F1, P1) and nothing else; never a folder or a whole file. The query embedding gets 1 s here, not search's 250 ms, since the answer takes seconds anyway; on a timeout it's keyword-only, as search is.
- **Every claim cites, and the citations are checked.** `claude-sonnet-5-5` at low effort, with the server-side refusal fallback, returns structured output: a list of sentences, each with its citations. At our boundary a citation survives only if it names a source the model was shown, and a cell only if it was one of the cells shown; a sentence left without a citation is dropped, and an answer left without a sentence says "The lab's records don't answer this." with the closest files under it. Sentences are checked and shown one at a time as the reply streams, then the whole reply is checked again and saved.
- **A citation opens what it cites**: the file (in Dropbox, or from our store), its table in the chart builder for a cell, or the protocol at the version cited.
- **Cache, ledger and cap.** The cache key is the sha256 of the prompt version, the model, the normalized question and the exact sources block, so the same question over the same records costs nothing the second time, and a new file or protocol version asks afresh. Every paid call is a `model_calls` row (purpose `answer` or `suggestion`), which now keys by that cache key when a call reads no one file. `labs.ai_monthly_cap_usd`, $25 by default, caps a calendar month's (UTC) questions and suggestions together; past it, asking says so and when it opens again, and cached answers still come back. The cap is checked before a call, so two questions at the same moment can pass it by one answer.
- **History and feedback.** Every question is saved with its checked answer and sources; the Search home lists the lab's latest four, each opening its saved answer (`?ask=<id>` reopens one). Each member can mark an answer helpful or not helpful once and change their mind.
- **The answer has its own box and shows its work as it happens.** The operator asked for the answer to look apart from the search results, "like a little box", with its tool calls streamed and drawn rather than written out. The answer sits in a raised card with a hairline border above the results, headed "Answer from the lab's files", with a close button; feedback and the two suggestion buttons are its footer. While it streams, an activity list shows each step the server ran, sent as `step` events on the same NDJSON stream: the search (a spinner, then a check and what it found, "by matching words" when the embedding timed out), a chip for each file whose passages it read, for each protocol with its version and for each parsed table with the rows and filled cells shown, then "Writing the answer", which hands off to the sentences. Nothing is drawn that didn't run: there's no writing step past the cap or after a search that found nothing. Steps that arrive together are shown at most 45 ms apart (all at once with reduced motion), the sentences wait for the list to catch up, and nothing else is delayed; each step rises 4 px and fades in over 180 ms. When the answer is in, the list folds to one line ("Searched once · read 5 files, 1 protocol and 1 table"), which opens it again. Citation numbers now follow the order the answer first cites a source, so a number never changes while sentences stream; pointing at a number lights its chips and its source row, and pointing at a chip lights its numbers. On a cache hit retrieval still runs (the cache key holds the sources block), so its steps are real, and the last one says "Answered before from these same files". The steps are saved with the answer (`questions.steps`, migration 0022, through `record_answer`'s new `p_steps`), so a question opened from Recent questions shows the steps it took, not steps rebuilt from its sources; answers saved before have none and show no list.
- **Approval is enforced by the database.** What the model says reaches the database only through `record_answer`, `record_suggestion` and `record_spend`, which only the service role may call and which insert questions, open suggestions, ledger and audit rows, nothing else. Members only read those tables. Our server reaches the three through a writer with exactly those methods. Approving runs as the member: a protocol edit saves through `save_protocol` on top of the version it was drafted from (the fork), so the version is theirs and a save by anyone since fails it; label fixes apply through `correct_label` for the files they keep checked, so each is their correction and undoable like any other. `settle_suggestion` marks a suggestion approved only when it finds that version or those corrections, made by the caller in the same transaction. Approve, edit first (the same save with their own title, text and note) and dismiss are each one click, and `suggestion.create`, `suggestion.approve` and `suggestion.dismiss` go to the audit log beside `question.ask`.
- **The diff ignores step numbers.** Inserting step 4 renumbers every step after it; lines compare without their leading number, so the diff shows one added step instead of the rest of the protocol removed and re-added.
- **Suggestions are drafted at medium effort** with the same checks: an edit needs at least one cited file and a body that differs; label changes may name only the lab's own experiments and people and only files the question's sources held, and a change that matches the current label is dropped.

## 2026-11-05 — dates along x

A column of dates or date-times is a third column kind, `date`, beside numbers and text, and a line or scatter chart puts it on a time axis. Parser version 2 (`workers/src/bl_worker/table_dates.py`).

- **What reads as a date.** ISO (`2026-11-03`, with `T` or a space and a time, fractions and an offset), `yyyy/mm/dd`, day and month with slashes, dots or dashes and a 2 or 4 digit year, with a 24-hour or AM/PM time, month names (`3 Nov 2026`, `Nov 3, 2026`, `4-Nov-2026`), instrument stamps with no separators (`20261103_174412`), cells an Excel workbook formats as dates, and plain Excel serial numbers under a header with "date" or "time stamp" in it, between 20,000 and 80,000 (1954 to 2119) so counts and volumes aren't taken for dates. A column is dates when more than half its filled cells are; the rest are counted as "not dates". `h:mm:ss` alone stays a duration in minutes, hours or seconds, as before.
- **Day or month first is decided per column.** A 13th or later in either place settles it for the whole column. When either order fits every date, the one that keeps the rows in time order wins (a log runs forward); when both do, slashes read the US way and dots and dashes the European way. A column whose dates fit neither order consistently stays text. The column carries a note ("Read as day/month/year." or "Read as month/day/year, since it keeps the rows in time order. Check a date you know."), shown under its name in the builder and under the chart.
- **Wall-clock time, never shifted.** Values are milliseconds since 1970 of the time as written, formatted in UTC, so a chart prints what the instrument printed whatever the reader's time zone, as label dates never shift. A column that writes offsets is converted to UTC and says so in its note.
- **Ticks.** 1, 2, 5, 10, 15 and 30 seconds or minutes, 1, 2, 3, 6 and 12 hours, 1, 2 and 7 days, then 1, 2, 3 or 6 months and years, near one tick per 90 px. Each tick names the coarsest unit that changes: `06:00`, then `Nov 4` at midnight; `Nov 3`; `Dec`, then `2027` in January. Readouts and "Show the numbers" print `Nov 3, 2026, 17:44` (seconds when the value has them). A time axis's From and To are date pickers and it has no unit field. Bars take a date column as categories, printed the same way.

## 2026-11-05 — per-series x columns

An AKTA or UNICORN export gives each curve its own volume column, each of its own length (the SEC fixture's UV curves have 961 points to 24 ml, its conductivity 241 points at 0.1 ml). A series may now name its own x column; the chart's x stays the default and most charts never see the choice.

- **Only where it makes sense.** The builder offers "Along x" when the table has another column of the same kind as x: other dates on a time axis, or columns in x's own unit (the AKTA volume columns, all in ml). Bars share one x. A series can't read along a column another series plots.
- **Each series is read along its own rows,** so the x range covers every series, and the hover readout lists each series at the place under the pointer: by row for series on the chart's x, by nearest point (within 12 px) for the others. "Show the numbers" lists every column a series reads.
- **Proved on the SEC fixture:** against the UV volume, conductivity was squeezed into the first 6 ml; on its own column it runs the full 24 ml and its points sit within a pixel of the UV trace at the same volume (`chart-geometry.test.ts`). One axis still: conductivity in mS/cm is its own chart, under the UV chart on the protocol page, not a second scale.
- `chart_spec_ok` takes `x` per series (a column letter or null, never on bars); old specs have none and keep the shared x.

## 2026-11-05 — plate heatmaps

A table that is a 96- or 384-well plate offers a Plate chart: round wells colored by value, row letters down the side, column numbers across, and the scale under it.

- **Three shapes of plate are found** (`lib/plates.ts`): a grid (a text column of row letters A, B, … and number columns named 1 to 24, which the parser keeps under a blank corner), a list (a column of well names, `A1` or `A01`, for most of the table, numbers beside it and an optional label column such as Sample), and a kinetic read (a number column per well, a row per read, and a time column). 384 is chosen when a row past H or a column past 12 appears. - **One hue, light to dark.** The dataviz reference blue in five steps, low to high, mixed in OKLab between steps (CSS `color-mix` on screen, the same mix in hex for export). Light theme `#86b6ef #5598e7 #2a78d6 #1c5cab #0d366b` on `#fbfbfb`; dark theme `#184f95 #256abf #3987e5 #6da7ec #b7d3f6` on `#151516`, so a low value recedes into the page in both. ## 2026-11-05 — more than six series

Lines take 12 series, bars 6 and scatters 3. The dataviz method never generates a seventh hue; it repeats hues with a second encoding. Past six, a line chart's series take the same six hues again, dashed (`6 4`), with hollow markers and a dashed legend key, and lines past six draw no point markers. The style is chosen per series: the first hue and stroke nobody has, solid first; no two series may share both. Bars stop at six, since no second style reads at bar widths. Scatter keeps its three, the most that pass the all-pairs check.

No new colors, but the order now wraps (green, the sixth, sits beside blue, the seventh): the validator on the seven-step sequence passes in both themes, worst adjacent CVD ΔE 9.2 light and 9.4 dark, normal vision 27.6 light and 19.7 dark; aqua and magenta stay under 3:1 on the light surface, which the legend and "Show the numbers" cover. ## 2026-11-05 — re-parsing tables

When the table parser's version rises (now 2), the worker's `sweep_stale_tables` runs every minute and queues up to 10 stale tables, ready or failed at an older version, as `reparse_table` jobs (the same lock as `parse_table`): about 600 an hour, each a download from where the file lives, so new files, parsed as they're processed, aren't crowded out.

- **Oldest used first.** A table's last use is the later of when it was asked for (or first parsed) and when a chart of it was last saved; idle tables go first, so tables people are working with move last.
- **The old table stays until the new one is in.** A version 2 table is stored at `<sha256>.v2.json`, a new key, and the row moves to it in one transaction; the old object is deleted after the commit, and a reader that loses that race reads the row again once. A re-parse that fails (the parser can't read it, or the file can't be read) keeps the old table and records `reparse_version` and `reparse_error` on the row, so the sweep moves on until the next version. A failed table that now parses becomes ready.
- **Idempotent and safe to stop.** Each job checks the row is still stale under the table's lock; progress is the rows' own parser versions (logged each sweep as "N at v2, M to go, K kept old"), so there are no counters to drift.
- **A saved chart is never changed.** If its columns went or changed kind, the chart's page says which ("The file was read again, and Rep 4 (column H) isn't in Standards as before.") with Fix the chart, which drops what went and keeps the rest; the protocol page says the same with a link.

Measured: in `scripts/e2e-charts.sh`, the five fixture tables marked as version 1 were read again by the real worker 21 s later, at the next minute's sweep, with their charts unchanged.

## 2026-11-05 — charts round 1: layouts, replicates, fits and tests

Round 1 of the chart plan: the science behind the charts, and the charts that need it. A plate's wells can now say what they are, repeats are summarized from the repeats themselves, and the chart that answers the question fits, tests and says what it did in plain words first and the technical name second. All math is plain TypeScript (`lib/stats.ts`), deterministic, never a model.

- **A sample layout** (`lib/layouts.ts`) says which wells are blanks, controls, standards (with their amount) or samples (with a name, and a dose or a dilution). Wells with the same role, name, amount and dilution are repeats; the layout keeps them as one group, so "which wells repeat each other" needs no second notion. It comes three ways: read from the export (a plate listed by well with a Sample column, plus Conc and Dilution columns when there are; or a Gen5 layout block of `BLK`, `CTL`, `STD1`, "Drug A" with a concentration grid, which the parser now keeps as a table, parser version 3), painted on the plate picture (drag, shift-click or tap a row letter or column number; Blank, Control, Standard, Sample; a dilution series from a start, a factor and a direction; a grid pasted from a spreadsheet), or a saved one. A layout saved on a protocol is offered for that protocol's next plate ("Use the layout from …"). Saved layouts are `sample_layouts` (0023), with RLS for members, column grants, `layout.create/save/delete` audit rows and `layout_ok` mirroring the zod schema key for key; they're in deletion's `LAB_TABLES` and blob references.
- **A chart keeps its own copy of the layout** in its spec (with the id it came from), so changing or deleting a saved layout never changes a saved chart. Provenance: a saved chart now records the protocol version it was saved on (`charts.protocol_version_id`, set by the database, never by members), and its page says "Made from" the file and sheet, the wells and the layout, and the protocol and version, with links.
- **Repeats come from the sheet's own shape** when there's no plate (`lib/replicates.ts`): "Rep 1…n" columns (several series when a name heads each set, as "Wild type" over Rep 1–3), a group column beside a value column, or a short sheet of numbers where each column is a group. Means in the sheet are passed over: the mean, SD, SEM and 95% CI are computed from the repeats. n is stated; every repeat is drawn when there are 10 or fewer (a box plot always draws them).
- **The blank** is the mean of every blank well or row; "Subtract the blank" takes it off every reading, is on whenever there are blanks, and the sentence and the figure's caption say so with the blank's mean and n.
- **Spreads.** SD (sample, n − 1), SEM (SD/√n) and the t-based 95% CI (t(0.975, n − 1) × SEM), each with a sentence on what it means; SD by default. Fewer than two repeats shows the mean alone and says why.
- **Tests, never chosen silently.** The builder starts on the test that fits and says why in a line: two groups, Welch's t-test (no equal-variance assumption, so no Levene step to explain); three or more with a control, each against the control by Welch's t-tests with Holm's step-down correction (uniformly more powerful than Bonferroni, valid without the equal-variance assumption Dunnett's needs); three or more without one, one-way ANOVA. None when the groups are standards or single values. A test picked by hand says so and names the suggestion; a group with n < 3, unequal spreads under ANOVA (largest SD over three times the smallest) and a box plot under 5 values per group are warned about. The answer reads "Unlikely: Welch's t-test, p = 0.0002"; the hover explains p in a sentence ("a gap at least this big, either way, would turn up by chance about 2 times in 10,000 experiments like this one"), with t, df and the means. Holm-corrected p is reported, with the uncorrected one in the explanation. Stars are optional and appear only with the test and the star key written under the chart.
- **Straight lines** (scatter of means, "like a standard curve"): least squares, or through the origin. R² is 1 − SSres/SStot about the mean of y for both, so the two fits compare; through the origin it can fall below zero, and it reads lower than Excel's or R's through-origin R², which measure about zero (said in its explanation). The equation and R² are on the chart; the line is solid across the standards and dashed past them. Fitted to the means of the standards, as the lab's checks do. Samples are read off it as (reading − intercept) ÷ slope, times their dilution, into a table with its own CSV download and a mg/mL (or nM, mM) switch; a sample outside the standards keeps its number with a "?" and "Outside your standards, so this number is a guess" in both columns, and the warning says what to do.
- **Dose-response.** A four-parameter logistic on log10 of the dose, y = bottom + (top − bottom) / (1 + 10^((logIC50 − x) × hill)), by Levenberg–Marquardt from nine starts, best minimum kept; top above bottom, so a falling curve has a negative Hill slope (Prism's inhibitor convention) and is an IC50, a rising one an EC50, and the chart says which. The 95% CI of the IC50 is asymmetric, from the covariance of logIC50 (SSR/(n − 4) × (JᵀJ)⁻¹, as `curve_fit`'s pcov) with t on n − 4 df. It is the relative IC50, halfway between the fitted top and bottom, and says so. **Fitted to every well by default**, not the means: with 5 doses and 4 parameters, a fit to means has 1 degree of freedom and a CI too wide to use, while the wells give 11; More options has "The means". The control (dose 0) has no place on a log axis, so it's a dashed line at its mean, labelled. Honest refusals, each in plain words with no number: fewer than 5 concentrations; no convergence; a flat curve (the extra sum-of-squares F test against a flat line, p ≥ 0.05); a step between two doses (the curve's 10–90% span under half the gap, so any steep curve fits); an IC50 outside the doses tested ("Test higher doses"); a CI that runs past them ("isn't pinned down", the number only as "about"). n says the wells are technical repeats.
- **Box plots and histograms.** Quartiles by linear interpolation (NumPy's default, Excel's QUARTILE.INC, R type 7), whiskers to the furthest value within 1.5 × IQR (Tukey), the rest as outliers; stated on the chart. Bins by the Freedman–Diaconis width (2 × IQR × n^(−1/3), Sturges when the IQR is zero) rounded to 1, 2 or 5 × 10^k so they read as "1 µm", on multiples of the width, each holding values from its left edge up to its right (the last closed, as NumPy); stated, with Narrower, Wider and a typed width.
- **Lines with a spread**: a line through the means with SD, SEM or CI as a 16% wash of the hue, or error bars. **Log x** on x/y charts and curves; zero or below refuses with the row named rather than dropping points.
- **The guide.** "What do you want to show?" offers three kinds suggested for the sheet, each with why in a line ("Drug A is at 5 concentrations with a control, 3 wells each, so a dose-response curve finds where it has half its effect (its IC50)"), and the rest under "Other kinds of chart" with the reason any can't be made. Kinds are what a student picks (Line, Bars, Scatter, Dose-response, Box plot, Histogram, Plate); each starts as a chart of repeats when there are some and as the sheet's own columns when not. A plate without a layout suggests its heatmap and offers "Mark the wells" (or a saved layout); after marking, the question comes back with what the layout now suggests. New controls sit where a beginner looks (what the bars show, every repeat, the blank, the test, the fit, bin width); scales and how a dose curve is fitted wait under More options.
- **Export.** "Single journal column (85 mm)", "Double column (180 mm)" or "Slides"; print sizes are laid out at 413 and 874 units so the 12-unit tick labels print at 7 pt, and their SVG says its width in mm. PDF (vector, a 300-line writer of our own SVG, `lib/pdf.ts`, Helvetica so nothing is embedded, loaded only when asked, so the builder's chunk doesn't carry it), SVG, PNG at 300 dpi for print sizes and 2× for slides, and the numbers behind the chart as CSV (every group's n, mean, SD, SEM, CI, its repeats by well, the test with t/F, df and p, the fit's parameters and the samples), unrounded. The test, the fit, what the bars show and the blank are written under the exported chart.
- **Colors.** One hue for one series (blue), bars behind their own dots at 28% of the hue mixed into the surface, samples on a curve in the second hue (orange) as diamonds, hollow when outside the standards; series past one take the existing validated order. The painter's roles carry a letter (B, C, S) or the amount in each well as well as a tint, so no role is color alone.

## 2026-11-05 — going online: hosts and how they fit

Landing and app on Vercel (two projects, roots `apps/landing` and `apps/web`, the app at `app.<domain>`), Supabase on Pro for the database and sign-in, R2 for files as before, the worker as one always-on Fly.io machine with no public address, and the search model on Modal with one L4 GPU that scales to zero. Resend becomes Supabase's mail server. `docs/deploy.md` has the steps, the variables and the bill (about $70 to $85 a month). Choices made while preparing it:

- **The worker embeds file chunks through the Modal service, not in its own process.** `RemoteEmbedder` sends 32 chunks at a time to `POST /embed/documents`, the batch endpoint `embed_api.py` now serves beside `/embed`, with the same key; `EMBEDDER=remote` picks it, and dev keeps `EMBEDDER=local`. The service checks the model name on every answer, so remote and local vectors never mix. Measured on the M4 Mac with the sample lab chunked the way the worker does it (51 files, 132 chunks, 23,764 Qwen tokens, a mean of 466 tokens a file, median 96): `embed_documents` ran at 968 tokens/s on MPS, 478 tokens/s on 2 CPU threads in fp32, and 22 tokens/s on 2 CPU threads in bfloat16, the dtype the model loads in by default. A 20,000-file lab like the sample is 9.3 million tokens. In process on Fly it would take about 5 hours if a dedicated Fly vCPU matched an M4 thread, likely 10 or more since it doesn't, and about 86 hours on a shared CPU throttled to its 1/16 baseline; the machine would also need about 8 GB for torch and the model beside the worker's files, about $90 a month instead of $25, every month, and the image would grow by about 4 GB of torch. On the L4 the same scan is an estimate, since nothing ran on Modal: at 10,000 tokens/s (ten times the Mac's GPU, a fraction of the L4's bf16 rating) it's 16 minutes and $0.21; at 2,000 tokens/s, 78 minutes and $1.03. Either way the GPU isn't what limits a first scan; Dropbox downloads and reading PDFs on the worker are.
- **Queries need the GPU too, and the old CPU number was bfloat16.** The 563 ms CPU query in "measured: query embedding and scan" matches bfloat16 (710 ms here on 2 threads); in fp32 the same CPU did 231 ms, still at the 250 ms budget on a fast laptop core and over it on a server vCPU. So queries stay on Modal as planned. Modal keeps the default bfloat16, as dev Macs do, so stored vectors match; an L4 runs bf16 natively and a T4 doesn't, which is why L4 over the cheaper T4.
- **Modal scales to zero after 5 idle minutes** (`workers/modal_embed.py`): weights baked into the image, the model loaded once per container, 16 requests at a time on one container with the GPU taking one batch at a time, at most 2 containers. The first search after a quiet spell runs on exact words while the GPU wakes, as any embed failure does. The idle window is most of the cost: about 7 container-minutes per search session, $11 to $41 a month for 5 to 20 sessions a workday, before the $30 monthly credit. `workers/scripts/measure_embed.py` measures the cold start, warm p50 and p95, and chunk throughput against the real service; memory snapshots are the next step if the cold start is over about 20 s.
- **The worker image has no torch.** `sentence-transformers` moved to a `local-embed` dependency group that `uv sync` still installs by default; the Dockerfile installs with `--no-default-groups`. The production dependencies take 142 MB installed (measured on macOS), and ffmpeg comes as one static binary (`mwader/static-ffmpeg`, 124 MB compressed) instead of Debian's package and its libraries. The image is roughly 400 MB uncompressed, an estimate: there was no Docker to build it here.
- **4 GB, measured.** With the remote embedder, `bl worker --concurrency 4` started at 80 MB and peaked at 509 MB on the sample lab plus a 400 MB file: a file in flight costs about 1.07 times its size, since sources read files whole. Four jobs on files at the 500 MB cap would need about 2.2 GB, so 2 GB isn't enough and 4 GB is. A Dropbox file over about 3.5 GB would still run the machine out of memory; that's the known gap in the worker README, now with a number on it. `fly.toml` runs one process with restart policy "always", and `bl migrate` as the release command. A first scan runs on performance-2x for the day (about $2.20), because a shared CPU is throttled to 1/16 of a core once its burst runs out.
- **Bench uploads and talk-through recordings go straight to R2**, closing the "presigned PUT" item in "uploads: the first slice". Vercel functions take at most 4.5 MB per request. `POST /api/uploads` now checks the type and size and answers with a presigned PUT (size and type signed in, 15 minutes) to `<lab_id>/uploads/<id>`; the browser PUTs the file there, then `POST /api/uploads/<id>/complete` has the server read it back, check its size and the sha256 the page computed, keep it at `<lab_id>/files/<sha256>` and record it, as the video and instrument paths do. It's the same core (`lib/staged-upload.ts`), with one PUT in place of parts for files up to 100 MB. A page without `crypto.subtle` (plain http on a LAN address in dev) sends no hash and the server's own stands. With the local store, the PUT goes to `/api/uploads/<id>`, so dev and tests run the same three steps. What a file is (name, experiment, date, or a talk-through's page) rides in the same headers as before, now on the complete call.
- **A bad environment stops a deploy, not a request.** The app's production check (`src/env.ts`) runs in `next.config.ts` at build and in `instrumentation.ts` at startup when `VERCEL_ENV` or `BINARY_ENV` is production, and lists every missing or malformed variable at once: https for Supabase, Dropbox and the embed service, a 32-byte token key, R2 as the store. The worker's runs at startup with `BINARY_ENV=production` and checks the same kinds of things plus ffmpeg and the embedder's library. Dev and tests check nothing new. Tests hold the three `.env.production.example` files to what the code reads.
- **Vercel installs with pnpm 12.16.1 through npx**, because the app's lockfile carries pnpm 12's own entry, which the pnpm Vercel picks by default doesn't read. Functions run in `iad1`, next to Supabase's us-east-1. Production variables are scoped to Production only, so preview deployments can't reach the live database. Fixture pages stay out of production builds: `*.dev.tsx` pages exist only under `next dev`, and `scripts/predeploy-check.sh` fails if any lands in `.next`.

Open: nothing here has run against a real Vercel, Fly, Modal, R2, Resend or Supabase account; `docs/deploy.md` ends with what that leaves unproven. Staged files from an upload that never completes (the PUT went up, the complete call never came) stay under `<lab_id>/uploads/` until the lab is deleted; R2's lifecycle rules filter by prefix only, and staging keys start with the lab id.
